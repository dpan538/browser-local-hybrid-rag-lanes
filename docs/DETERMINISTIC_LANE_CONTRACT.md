# Deterministic Lane Contract

Generated: 2026-06-09

This document fixes the first-version definition of deterministic lanes.

## Decision

The first version uses rule-based routing plus exact rendering from structured
retrieved evidence fields.

It does not use:

- a small model to decide deterministic lanes;
- distilled classifiers;
- free-form model paraphrase for source/rights fields;
- OCR or document extraction inside the deterministic lane.

This makes the contribution a browser-local RAG systems/methodology question:
given retrieved structured evidence, which answer lanes should be rendered by
the runtime rather than generated by the local model?

## What Deterministic Means

Deterministic means:

1. The lane is selected by an explicit rule or fixture label.
2. The output is assembled from known fields in the evidence packet.
3. Contract-bearing fields are copied or normalized by fixed rules.
4. No local language model generates the contract-bearing values.
5. Latency is reported as `hybrid_system_latency`, not
   `qwen_generation_latency`.

## What Deterministic Does Not Mean

Deterministic does not mean semantic truth is guaranteed.

If a source record, OCR pass, metadata extraction step, or fixture field is
wrong, deterministic rendering will preserve that wrong field. The lane
guarantees rule-conforming output from evidence; it does not guarantee that
the evidence itself is correct.

This distinction creates two separate contracts:

| Contract | Question | Example Metric |
|---|---|---|
| Evidence-to-output fidelity | Did the system render the provided evidence according to rules? | exact field preservation |
| Evidence correctness | Was the provided evidence itself true relative to the source document? | source audit correctness |

The first contract is in scope for deterministic lane automation. The second
requires source/document audit and should be reported separately.

## Contract-Bearing Fields

Initial contract-bearing fields:

- `record_id`;
- `title`;
- `source`;
- `source_name`;
- `source_domain`;
- `rights_label`;
- `rights_state`;
- `reuse_permission`;
- `public_domain_status`;
- `image_state_code`;
- `image_state_label`;
- `date_text`;
- refusal labels such as missing evidence or missing chronology proof.

## Metrics

Required deterministic lane metrics:

- `deterministic_lane_applicable`: whether rules say the row belongs to a
  deterministic lane.
- `deterministic_lane_selected`: whether the runtime selected that lane.
- `evidence_to_output_fidelity`: whether required evidence fields were
  preserved.
- `field_omission_count`: number of required fields missing from output.
- `field_mutation_count`: number of required fields changed by output.
- `unsupported_upgrade_count`: number of rights/status claims made beyond
  evidence.
- `source_audit_status`: `not_audited`, `pass`, `fail`, or `uncertain`.
- `source_audit_notes`: short human/source-audit note when available.

## Reporting Rule

A deterministic lane pass means:

The system followed the deterministic rendering contract over the supplied
evidence.

It does not mean:

The upstream metadata is complete, OCR is correct, the source archive is
authoritative for legal purposes, or the output is independent legal advice.

## First-Version Lane Assignment

For the first reproducible experiment, lane assignment should be explicit and
auditable:

- fixture label defines the intended lane;
- a small rule table maps labels to execution modes;
- no learned router is used;
- any later learned or model-assisted router must be evaluated as a separate
  ablation.

This avoids blending three different research questions:

- RAG/system policy: rules plus exact evidence rendering.
- Retrieval question: whether the correct evidence was retrieved.
- Efficiency/model question: whether a learned model can replace the rule.
