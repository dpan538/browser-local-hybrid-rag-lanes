## Position

This direction is sufficiently independent to support a paper thread:

Hybrid answer lanes ask a different question from the main Qwen/WebLLM
performance experiment. The main line asks whether a browser-local
0.8B-class WebLLM/Qwen RAG run can satisfy contract and latency requirements.
This parallel point asks which parts of an answer should be generated at all.

The strongest framing is:

What should not be generated by a local small model in browser-local RAG?

For rights-aware archive assistants, some user requests require exact evidence
delivery rather than free-form prose. Rights labels, source URLs, image-state
caveats, public-domain status, and mandatory refusals are better understood as
contract-bearing fields. A small local model can still be valuable for
explanation, comparison, synthesis, and research guidance, but it should not be
asked to paraphrase fields where paraphrase creates risk and latency without
adding user value.

## Primary Literature Synthesis

### Browser-local LLM inference

WebLLM establishes browser-local LLM inference as a real systems target using
WebGPU and WebAssembly, with an OpenAI-compatible API and browser-side model
execution:

- WebLLM paper: https://arxiv.org/abs/2412.15803
- WebLLM repository: https://github.com/mlc-ai/web-llm
- MLC WebLLM docs: https://llm.mlc.ai/docs/deploy/webllm.html

Related browser runtime paths strengthen the systems context:

- ONNX Runtime WebGPU execution provider:
  https://onnxruntime.ai/docs/tutorials/web/ep-webgpu.html
- Transformers.js WebGPU guide:
  https://huggingface.co/docs/transformers.js/guides/webgpu
- LlamaWeb WebGPU inference:
  https://arxiv.org/abs/2605.20706

Takeaway: browser-local inference is covered. The open point is not whether the
browser can run a model, but how a browser-local assistant should allocate work
between model generation and deterministic runtime/UI logic.

### Browser-local retrieval and private RAG

MeMemo is the most direct browser-local retrieval neighbor. It adapts HNSW to
browser environments and supports local dense retrieval with IndexedDB and Web
Workers:

- MeMemo project: https://zijie.wang/papers/mememo/
- MeMemo paper: https://arxiv.org/abs/2407.01972
- MeMemo code: https://github.com/poloclub/mememo

Takeaway: private browser-local retrieval is covered. The open point is
generation policy: MeMemo-style retrieval does not decide which answer fields
should bypass generation for contract or latency reasons.

Takeaway: prior work evaluates whether generated answers are supported by
retrieved evidence, and whether retrieval should be corrected or critiqued.
The parallel point goes one step earlier: if the evidence already contains the
answer as a contract-bearing field, the correct behavior may be not to
generate.

### Deterministic guardrails, neuro-symbolic systems, and structured generation

Structured/constrained generation sources add useful neighboring context:

  https://arxiv.org/abs/2212.06094

Takeaway: prior work constrains, routes, or structures generation. Hybrid
answer lanes differ by saying that some lanes should not generate at all; the
runtime should render exact evidence or refusal outputs directly.

### UI/runtime-mediated AI systems

Human-AI interaction and mixed-initiative work support treating UI/runtime
layers as part of the AI system rather than neutral display shells:

- Principles of Mixed-Initiative User Interfaces:
  https://www.microsoft.com/en-us/research/wp-content/uploads/2016/11/chi99horvitz.pdf
- Guidelines for Human-AI Interaction:
  https://www.microsoft.com/en-us/research/publication/guidelines-for-human-ai-interaction/
- AI Chains:
  https://arxiv.org/abs/2110.01691

Takeaway: UI/runtime mediation is a legitimate design object. For archive RAG,
the UI/runtime layer can be the trustworthy component that preserves exact
source/rights fields and exposes when evidence is insufficient.

### Latency accounting for hybrid AI systems

LLM serving work normalizes phase-specific latency reporting:

- vLLM / PagedAttention:
  https://arxiv.org/abs/2309.06180
- DistServe:
  https://arxiv.org/abs/2401.09670
- WebGPU dispatch overhead:
  https://arxiv.org/abs/2604.02344
- Efficient tool use with Chain-of-Abstraction:
  https://arxiv.org/abs/2401.17464

Takeaway: latency should be attributed to system phases. For this branch, the
paper-safe reporting rule is:

- `qwen_generation_latency`: time spent in local model generation.
- `hybrid_system_latency`: end-to-end user-visible answer latency after
  retrieval, deterministic rendering, contract checks, optional generation, and
  UI/runtime assembly.

If a deterministic lane skips generation, it must not be reported as faster
Qwen generation.

## Independent Paper Value

The direction is independently valuable because it is not merely a local
optimization. It reframes small-model RAG as a division-of-labor problem:

- What is evidence delivery?
- What is explanation?
- What is refusal?
- What is synthesis?
- Which component should own each?

The strongest paper contribution would not be "hybrid lanes are faster" alone.
It would be:

1. A taxonomy of browser-local RAG answer lanes by generation necessity.
2. A contract-aware routing policy for deterministic vs generative execution.
3. A latency accounting protocol that prevents model-speed overclaiming.
4. An archive-grounded evaluation showing that some high-trust answer classes
   are safer and faster when not generated.

## Candidate Claim

A browser-local small-model RAG assistant is most credible when it treats the
small model as a bounded synthesis component, not as the universal answer
surface. Deterministic UI/runtime layers should own exact evidence-field
delivery and hard refusals; the small model should own explanatory, comparative,
and research-guidance prose.
